# 产品经理全流程 Skill 套件设计

状态:已确认,待实施
日期:2026-10-12
来源需求:https://gaotuedu.feishu.cn/wiki/JHFlwZ77ZixFGakuIDpcSlcZn8c (初步梳理文档,内容经行业方法论调研补充)

## 1. 背景与目标

把产品经理的标准工作流拆成 5 个阶段 + 1 个路由,每阶段对应一个可独立调用的 Claude Code skill,也可以在前一阶段质量门通过后自动询问是否进入下一阶段。目标是打造一套「切实可用」的产品经理 agent,而不是方法论的罗列——每个框架都要落地成可执行的评分模板、提问清单或自检表,不是摆个名词。

5 个阶段严格对应用户飞书文档的结构:①需求挖掘与收集 ②需求沟通与细节碰撞 ③需求甄别与价值判断 ④产品方案设计 ⑤原型设计与交互定义。

## 2. 与现有 skill 生态的关系

机器上已经装了 `sdd:pm-*`(15 个 skill,来自 qyxn-sdd-marketplace),但那套是面向 Spec-Driven Development 的工程契约范式(spec 是 AI 可执行合约,四层结构、OpenSpec 目录约定、`pm:define:spec` 这种冒号命名)。本套件服务的是经典 PM 工作流(需求池→澄清→价值判断→PRD→原型),两者范式不同,因此:

- **不并入** `sdd:pm-*` 命名空间,新套件统一用短横线前缀 `pm-collect` / `pm-clarify` / `pm-value` / `pm-prd` / `pm-proto` / `pm`,与 `sdd:pm-*` 的冒号命名共存不冲突。
- **借用约定**:输入面板(✅已确认/❌必须明确/⚠️已推断)、质量门判据(PASS/WARNING/BLOCKER)、中文写作规范(全角标点、技术术语保留英文、RFC 2119 风格的 MUST/SHOULD）。
- **委托而非重写**:原型阶段的 HTML 高保真原型生成直接调用已有的 `huashu-design` skill,不重新实现这个能力。

## 3. 套件总览

| 指令 | 阶段 | 职责 |
|---|---|---|
| `/pm` | 路由 | 查需求池现状,某需求定位到哪一步,给出下一步指令建议 |
| `/pm-collect` | ①挖掘与收集 | 记录一句话需求 → 标准化需求卡片 → 写入飞书需求池(首次调用自动建表) |
| `/pm-clarify` | ②沟通与澄清 | 生成结构化沟通提纲 → 用户线下谈完回填 → 产出「真实需求」结论 |
| `/pm-value` | ③甄别与价值判断 | 5 Whys + 刚需度/频次度/温度 + RICE + KANO + 俞军公式 → P0-P3 定级 |
| `/pm-prd` | ④方案设计 | 背景/功能清单/功能逻辑/业务流程图(Mermaid)/角色/用例/规则/状态机 |
| `/pm-proto` | ⑤原型与交互 | 交互规格(IA/5态/尼尔森自检/WCAG)→ 可选委托 `huashu-design` 出 HTML 原型 |

阶段串联方式:每个 skill 结束时跑质量门(PASS/WARNING/BLOCKER),PASS 后主动问「是否进入下一阶段」等待用户确认才继续;BLOCKER 则列出缺项,不询问是否继续(必须先补)。

## 4. 共享机制

所有六个 skill 遵守以下约定:

### 4.1 防伪造规则(最高优先级)

RICE 分、使用频次、刚需度打分等具体数字,只能来自三种来源:
1. 用户在对话中明确给出的数字或可推导的事实
2. 标注 `⚠️ 推断:[推断依据]` 的估算,依据必须写明
3. 没有依据时留空并标 `⚠️ 待确认`

禁止在没有依据的情况下虚构具体数字去填满一个看起来完整的表格——这是生成式 PM 文档最容易出问题、也最难被发现的地方。

### 4.2 输入面板(Step 0)

每个 skill 开场执行输入面板检查,格式:
```
✅ 已确认:[字段] = [值]
❌ 必须明确:[字段] → 影响:[不明确会导致下游什么问题]
⚠️ 已推断:[字段] = [推断值](依据:[原因])
```
❌ 项一次只问一个,不批量甩问题给用户。全部 ❌ 清空后才能进入正式流程。

### 4.3 需求 ID

格式:`REQ-YYYYMMDD-NNN-简短标题`(如 `REQ-20261012-001-订单导出`),`/pm-collect` 首次生成,后续四阶段共用,作为飞书记录主键和本地文件夹名。

### 4.4 质量门判据(反模式清单,来自方法论调研)

| 阶段 | BLOCKER 判据 |
|---|---|
| collect | 场景描述为空;紧急程度与场景描述矛盾(如标 P0 但场景写"不急") |
| clarify | 提纲未覆盖必答维度就直接回填总结;「真实需求」结论与原始诉求完全一致却未解释原因 |
| value | 命中"单一样本/竞品陷阱(竞品有所以我们也要)/老板需求未经验证/历史同类功能使用率为零"任一反模式而未被识别讨论 |
| prd | 只有主流程没有异常流;状态机存在不可达或不可退出的死胡同状态;字段缺少约束规则;验收标准不是 Given-When-Then 格式 |
| proto | 组件缺少 5 态(理想/空/错误/部分/加载)中的任一;未做尼尔森 10 原则自检;未标注关键 WCAG 数值 |

## 5. 逐阶段详细规格

### 5.1 `/pm-collect` —— 需求挖掘与收集

**目标**:建立统一需求入口,不做预判地记录"用户想表达什么"。严格区分记录(这一步)和判断(后续阶段)。

**必问字段(❌,缺了问,一次一个)**:
- 提出人、提出时间
- 来源渠道(枚举:用户反馈/客户投诉/市场调研/竞品动态/业务运营需求/老板战略方向/技术重构性能优化)
- 场景描述(什么情况下产生这个需求)
- 预期结果(用户期望看到什么)

**可推断字段(⚠️,标注推断依据)**:
- 紧急程度(根据措辞语气、是否提及截止时间等线索推断)

**处理原则**:原始诉求(Request)单独记录为一个字段,不在这一步替用户下结论"真实需求"是什么——那是 `/pm-clarify` 的职责。这一步只做忠实记录。

**产出**:
- 飞书需求池新记录
- 本地 `pm-workspace/requirements/<REQ-ID>/01-collect.md`

### 5.2 `/pm-clarify` —— 需求沟通与细节碰撞

**目标**:通过结构化沟通补充需求背景,还原真实使用场景,产出"真实需求"结论,与原始诉求对比。

**两步流程**(用户决策:提纲模式为主,支持回填):
1. **生成沟通提纲**,覆盖维度:
   - 用户角色(Who)、使用场景(Where/When)、核心痛点(What)——文档原有三要素
   - 触发条件、当前变通方案(workaround)、影响范围/人数、不解决的后果、成功判定标准、边界(明确不做什么)、依赖方——方法论调研补充的维度
   - 每条配 Mom Test 风格追问话术,问具体过去行为而非假设性意见。例:不问"你会用这个功能吗",问"上次遇到这个问题,你是怎么处理的,花了多久"
2. **回填结果**:支持贴文字、传本地文件、飞书文档链接、飞书妙记链接(自动拉取逐字稿)四种输入源,skill 自动识别类型

**产出**:
- 「真实需求」结论,与原始诉求（Request）并列展示差异
- 本地 `02-clarify.md`,飞书记录更新澄清组字段

### 5.3 `/pm-value` —— 需求甄别与价值判断

**目标**:过滤伪需求,评估投入产出比,确定优先级。

**评分流程**(全部模型都用,按顺序执行):
1. **5 Whys**:连续追问"为什么"直达本质,禁止在同一条链上跳步,每层回答都要记录
2. **刚需度/频次度/温度三维评分**:每维度打分需用户确认或标注 ⚠️推断及依据
3. **RICE**:
   - Reach:影响用户数(按时间周期计)
   - Impact:massive=3 / high=2 / medium=1 / low=0.5 / minimal=0.25
   - Confidence:100%(高)/ 80%(中)/ 50%(低),低于 50% 的点子不纳入计算
   - Effort:人月
   - 公式:(Reach × Impact × Confidence) / Effort
   - B端调节:Reach 对单一大客户诉求容易失真,需叠加战略契合度/合规要求/合同义务作为调节项,并说明理由
4. **KANO**:
   - 每个需求点配一组功能性问题("如果有这个功能你感觉如何")和非功能性问题("如果没有这个功能你感觉如何")
   - 答案 5 级量表:我喜欢这样/我希望这样/中立/可以忍受/我不喜欢这样
   - 两个答案组合查评估表,落入:必备型(M)/期望型(O)/魅力型(A)/无差异型(I)/反向型(R)/可疑型(Q,答案自相矛盾需重新确认)
   - Better-Worse 系数:SI(满意度增加量)=(A+O)/(A+O+M+I);DSI(不满意度增加量)=-(O+M)/(A+O+M+I)
5. **俞军用户价值公式校验**:用户价值 =（新体验 − 旧体验）− 替换成本。替换成本（用户迁移习惯、学习新操作、历史数据迁移代价）是最容易被漏算的一项,必须显式计算
6. **综合定级**:P0(核心主流程阻断/安全漏洞/高频高价值)/ P1(明显提升体验且可量化收益)/ P2(锦上添花)/ P3(伪需求/ROI极低/技术成本极高)

**产出**:评分表 + 定级结论,写回飞书记录价值组字段

### 5.4 `/pm-prd` —— 产品方案设计

**目标**:把业务需求转化为系统化的产品逻辑与流程。

**前置检查**:只有 P0-P2 的需求才继续往下走。若需求是 P3,这一步应拦截并询问用户是否仍要继续(可能有非量化的战略理由)。

**产出章节**:
- 背景
- 功能清单
- 功能逻辑
- 业务流程图:用 Mermaid `flowchart` 语法,含主流程 + 分支流程 + 异常流程(至少覆盖:支付成功/失败、退款、网络超时等对应场景的异常分支)
- 架构设计:信息架构(IA,菜单/页面层级)+ 功能结构图(模块拆解:增删改查/导出/权限控制)
- 角色说明
- 用例说明:遵循 INVEST 原则(独立/可协商/有价值/可估算/小/可测试),验收标准用 Gherkin 格式(`Given <前置条件> When <触发动作> Then <期望结果>`)
- 规则定义:数据字段约束表(必填/选填/类型/长度/格式/默认值/唯一性/校验提示)、状态机(用 Mermaid `stateDiagram-v2` 语法)

**状态机完备性自检**(写进质量门):每个状态必须可达、必须可退出(无死胡同状态)、每条转换标注触发事件 + 前置条件 + 后置动作。

**异常流强制自检清单**:空态/加载态/错误态/无权限/离线/超时/部分失败/并发冲突/幂等重试——业务流程图章节下必须逐项过一遍,不适用的要写明"不适用"而非留空。

**产出**:本地 `04-prd.md`,飞书记录更新 PRD 链接

### 5.5 `/pm-proto` —— 原型设计与交互定义

**目标**:先产出交互规格,规格确认后再决定是否生成可运行的高保真原型。

**第一步:交互规格**
- 页面清单
- 信息架构
- 每个组件/页面的 5 态(UI Stack,Scott Hurff):理想态、空态、错误态、部分态、加载态——必须逐一填写,不能只做理想态
- 尼尔森 10 大可用性原则自检表(NNGroup 现行措辞:系统状态可见性/匹配用户心智模型/用户控制与自由/一致性与标准/防错优于纠错/识别优于记忆/灵活高效/简洁美学/帮助识别诊断恢复错误/帮助文档)
- WCAG 2.2 关键数值标注:正文对比度 ≥4.5:1,大字号/UI控件对比度 ≥3:1,触控目标 ≥24×24 CSS px,焦点必须可见,支持键盘操作
- 响应反馈节奏参考:0.1s 内无需特殊反馈,1-10s 需反馈但不打断,超过 10s 用进度条(Nielsen 三档响应时间 + Doherty 400ms 阈值)
- 主题色与语义色(primary/success/warning/danger/info)

**第二步:委托高保真原型**
质量门 PASS 后问用户:「是否调用 huashu-design 生成 HTML 高保真原型?」若用户确认,把交互规格文档作为上下文传给 `huashu-design`,由它完成 HTML 原型生成——`/pm-proto` 不重新实现这部分能力。

**产出**:本地 `05-interaction.md`,若委托生成原型则落在 `prototype/` 子目录

### 5.6 `/pm` —— 路由

- 无参数调用:列出飞书需求池中所有需求及其当前阶段(查询对应视图)
- 带需求 ID 调用:显示该需求的阶段历史(各本地 md 文件是否存在)+ 下一步建议指令

## 6. 数据与状态设计

**原则**:飞书多维表格存索引和结构化字段(团队可见、可筛选、可统计),本地存长文档(PRD、交互规格等),两边用需求 ID 对齐。

### 6.1 飞书多维表格字段设计

首次调用 `/pm-collect` 时如果检测到 `pm-workspace/config.json` 不存在或未配置需求池 token,询问用户要建在哪个文件夹,然后自动建表 + 建视图(按优先级看板、待澄清、待评估三个视图),token 写入本地 `pm-workspace/config.json`。

字段分五组:

| 分组 | 字段 |
|---|---|
| 采集组 | 需求ID、提出人、提出时间、来源渠道、场景描述、预期结果、紧急程度、原始诉求 |
| 澄清组 | 真实需求、用户角色、使用场景、核心痛点 |
| 价值组 | 刚需度、频次度、温度、RICE-Reach、RICE-Impact、RICE-Confidence、RICE-Effort、RICE综合分、KANO分类、优先级(P0-P3) |
| 交付组 | PRD链接、原型链接 |
| 流程组 | 当前阶段、更新时间 |

### 6.2 本地目录结构

```
pm-workspace/
  config.json                              # 飞书 app token、table id、字段映射
  requirements/
    REQ-20261012-001-订单导出/
      01-collect.md
      02-clarify.md
      03-value.md
      04-prd.md
      05-interaction.md
      prototype/                           # huashu-design 产出落地于此
```

每个阶段的 skill 读取上一阶段的本地 md 文件 + 飞书记录来恢复上下文,因此单独调用任何一个指令都能自己找到所需信息——这是"可单独调用"与"可自动串联"能同时成立的关键机制。

## 7. 实施顺序

遵循 superpowers:writing-skills 的 TDD 流程(每写完一个 skill 过一遍基线测试再继续下一个,不批量写完再测):

1. `/pm-collect` —— 最简单,优先验证飞书自动建表链路是否通畅
2. `/pm-value` —— 评分模型最多、最容易被滥用编造数字,风险最高,优先测试防伪造规则是否生效
3. `/pm-clarify`
4. `/pm-prd`
5. `/pm-proto`
6. `/pm`(路由)—— 依赖前五个已存在,最后实现

## 8. 技术前提(已验证)

- 飞书 auth 已就绪(user identity, token valid),具备 `base:table:create` / `base:field:create` / `base:record:create` / `base:view:write_only` 等所需 scope,自动建表链路可行
- `huashu-design` skill 已安装且成熟,有明确触发词,`/pm-proto` 第二步可直接委托,无需重新实现 HTML 原型生成能力
- `lark-base` skill 的 `references/lark-base-field-schema.md` 等参考文档齐全,建表时按需查阅即可

## 9. 已知限制

- 本次方法论调研中,「原型/交互阶段的 UX 原则」一路完整完成网络核验(尼尔森原则现行措辞、WCAG 2.2 数值、UI Stack、Gestalt 原则等均有可查来源);其余四个阶段(需求挖掘、澄清访谈、价值判断、PRD方案设计)的方法论补充未能完成网络二次核验(调研 agent 在执行中递归派生子任务耗尽了 API 配额),内容基于已确认可靠的既有知识(RICE/KANO/俞军公式/Mom Test/PRFAQ/Mermaid 语法等均为成熟公开方法论),但未逐条标注来源 URL。如需对某个具体数字做严格溯源(如 KANO 评估表的完整版本、DSDM 60% 经验值的原始出处),建议后续单独起一个范围收窄的调研任务。
