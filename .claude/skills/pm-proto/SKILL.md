# pm-proto · 原型设计与交互定义

## 触发

**触发词**:交互设计、原型规格、UI 状态、尼尔森原则自检、画原型、交互规格文档
**不触发**:业务逻辑还没定(→ `/pm-prd`)、要直接出 HTML 高保真原型而规格还没写(先走本 skill 第一步)

## 输入要求

### 必须有

- `04-prd.md` 已存在(本 skill 的页面清单和交互逻辑要对应 PRD 里的功能清单和业务流程)

### 多轮澄清原则(贯穿 Step 1-5)

本 skill 产出的交互规格有不少内容无法单靠 `04-prd.md` 直接推出,遇到以下情况时**先问用户一个具体问题,不要自己假设或编一个"看起来合理"的答案**:

1. Step 1 判断页面范围或组件边界时,如果 PRD 功能清单/流程图信息不足以确定某个页面是否存在,或者某个交互单元算不算需要单独定 5 态的"组件",先问用户,不要自己猜一个范围
2. Step 2 判断某页面/组件是主流程还是异常流程时,如果对应 PRD 流程图信息不足(比如流程图过于简化、看不出这个页面对应哪个节点),先问用户,不要按"看起来像主流程"这种直觉去分类
3. Step 2 填写空态/错误态等具体文案,或 Step 5 判断某操作是否需要特殊响应节奏时,如果产品有既定的文案规范/品牌语气要求,或者 PRD 没标"异步/耗时"但看起来可能耗时(比如涉及大数据量),先问用户有没有具体要求或预期耗时;用户说"你定一个就行/没有特殊要求",才可以给出默认方案,但要在产出里标注"⚠️ 默认方案,未经用户确认"

一次只问一个具体问题,不批量甩给用户。用户给出明确答案就用用户的答案;用户确认没有特殊要求,才按行业惯例/合理默认值处理,并标注这是未经确认的默认方案。

## 执行流程

### Step 0 — 输入面板

检查 `04-prd.md` 是否存在。

### Step 1 — 页面清单 + 信息架构

列出 PRD 功能清单对应的页面,画出页面层级(树状列表)。

对每个页面,进一步列出其中承担主要交互职责的组件(如列表、表单、关键按钮/操作入口);不需要穷举所有视觉元素,只列出会在 Step 2 定义 5 态的交互单元。本 skill 后续提到的"组件",就是这里列出的交互单元。如果 PRD 信息不足以判断某个页面是否存在,或者某个交互单元是否值得单独定 5 态,按"多轮澄清原则"先问用户。

### Step 2 — 每个组件/页面的 5 态(UI Stack)

判断页面/组件是否属于"主流程":对照 `04-prd.md` 对应功能模块 Step 6.2 的业务流程图——如果该页面/组件对应流程图里的主干节点(不在任何异常分支路径上),就算主流程;如果只出现在异常分支节点对应的页面/组件里,按异常流程处理(可以只填相关的几态)。如果流程图信息不足以判断,按"多轮澄清原则"先问用户,不要凭直觉分类。

**必须逐一填写,不能只做理想态**。空态/错误态等具体文案如果产品有既定的文案规范或品牌语气要求,先问用户;没有特殊要求,写一个合理默认文案并标注"⚠️ 默认方案,未经用户确认":

| 状态 | 要定义什么 |
|---|---|
| 理想态 | 正常数据下的展示 |
| 空态 | 没有数据时显示什么(不是空白页面,要有引导性文案) |
| 错误态 | 出错时的提示文案和恢复路径 |
| 部分态 | 数据部分加载/部分失败时怎么显示 |
| 加载态 | 等待时的反馈形式 |

每个 PRD 里标为"主流程"的页面/组件,这五态必须全部填写;异常流程对应的页面可以只填相关的几态,但要说明跳过的理由。

### Step 3 — 尼尔森 10 大可用性原则自检表

逐条检查交互设计是否违反以下原则(NNGroup 现行措辞):

| 原则 | 自检问题 |
|---|---|
| 系统状态可见性 | 用户任何操作后,是否有明确反馈? |
| 匹配用户心智模型 | 术语和流程是否符合用户已有认知,而非系统内部逻辑? |
| 用户控制与自由 | 是否有退出/撤销路径? |
| 一致性与标准 | 同类操作的交互方式是否统一? |
| 防错优于纠错 | 能否在用户犯错前就阻止,而不是事后提示错误? |
| 识别优于记忆 | 用户需要记住的信息是否最小化? |
| 灵活高效 | 是否对高频操作提供快捷方式? |
| 简洁美学 | 界面是否只保留必要信息? |
| 帮助识别诊断恢复错误 | 错误提示是否说明原因和解决方法? |
| 帮助文档 | 复杂操作是否有可查阅的说明? |

逐条写明"符合"或"需要改进",需要改进的给出具体修改建议,不能空泛写"待优化"。

### Step 4 — WCAG 2.2 关键数值标注

- 正文对比度 ≥ 4.5:1
- 大字号(18pt+)/UI 控件对比度 ≥ 3:1
- 触控目标 ≥ 24×24 CSS px
- 焦点状态必须可见
- 核心操作支持键盘完成(不依赖鼠标)

在交互规格里对涉及文字颜色、按钮尺寸的部分,标注对应数值要求。标注方式:每次描述一个具体元素(按钮/文字/交互目标)的样式时,直接在同一句话里用括号标注对应数值,例如"导出按钮(触控目标 ≥24×24px)"或"错误提示文字(对比度 ≥4.5:1)",不要只在文档开头统一列一次脱离具体元素的数值清单。

### Step 5 — 响应反馈节奏

- 0.1 秒内:无需特殊反馈
- 1-10 秒:需要反馈但不打断(如 loading 动画)
- 超过 10 秒:必须用进度条,且告知预估剩余时间

对应 PRD 里标为"异步/耗时"的操作(如 fixture 里的大数据量导出),标注预期响应时间档位和对应的反馈形式。如果 PRD 没有明确标注某操作是否耗时,但看起来可能涉及大数据量或外部依赖,按"多轮澄清原则"先问用户预期耗时,不要自己假设一个档位。

### Step 6 — 主题色与语义色

primary / success / warning / danger / info 五个语义色的使用场景说明(不需要给出具体色值,这是设计师的工作,PM 只需定义语义)。

### Step 7 — 质量门

**BLOCKER 判据**:
- 任一主流程组件缺少 5 态中的任一态
- 没有做尼尔森 10 原则自检(或自检表是空的)
- 没有标注任何 WCAG 数值

BLOCKER 命中时,本阶段不执行"产出写入 Feishu"和写本地文件的步骤,等补齐缺失的状态/自检/数值标注后再继续。

**PASS 时**,问用户:"`/pm-proto` 交互规格已完成。是否调用 huashu-design 生成 HTML 高保真原型?"

### Step 8 — 委托高保真原型(用户确认后)

如果用户确认,先检查 `05-interaction.md`(Step 6 语义色定义)和此前对话里是否提到过具体的 UI 视觉风格方向(比如参考哪个产品的风格、简约/科技感/国潮等调性、是否有现成的品牌视觉规范)。Step 6 只定义了语义色的使用场景,不等于视觉风格——没有视觉风格信息时,**先问用户一个问题**:"生成高保真原型前,你有没有具体的视觉风格要求(比如想参考哪个产品的风格,或者偏简约/科技感/其他调性)?如果暂时没想法,我可以让 huashu-design 帮你推荐几个方向。"

- 用户给出具体风格方向(或品牌规范链接/描述),把这个方向作为上下文一并传给 `huashu-design`
- 用户说"没有想法/你帮我推荐",明确告知 `huashu-design` 走它自己的设计方向顾问模式(该 skill 本身支持在风格不明确时推荐多个方向供选择),不需要本 skill 代为决定一个风格

拿到风格方向(或委托 huashu-design 自行推荐)后,把 `05-interaction.md` 的内容 + 风格方向作为上下文,触发 `huashu-design` skill 生成 HTML 原型。本 skill 不实现任何 HTML/CSS 生成逻辑,也不自己决定视觉风格,只负责把交互规格和风格信息整理成 `huashu-design` 能理解的输入。产出放在 `pm-workspace/requirements/<REQ-ID>/prototype/` 目录。

## 常见设计错误

> 只填了理想态,空态/错误态写"同理想态"或留空——这正是质量门要拦的 BLOCKER,UI Stack 五态存在的意义就是逼着不漏掉非理想情况。

## 质量检查(生成前自检)

- [ ] 主流程组件的 5 态全部填写,没有用"同上"偷懒
- [ ] 尼尔森自检表 10 条全部有具体结论,不是空表格
- [ ] WCAG 数值标注落到了具体的文字/按钮描述上,不是只在文档开头提一句
- [ ] 页面/组件范围、主流程分类、文案规范、响应耗时这几类判断,信息不足时是先问了用户,不是自己假设;给出的默认方案都标注了"⚠️ 默认方案,未经用户确认"
- [ ] 委托 huashu-design 之前,已有视觉风格信息才直接传,没有的话问过用户(或明确告知用户可以让 huashu-design 推荐),不是本 skill 自己替用户定一个风格
