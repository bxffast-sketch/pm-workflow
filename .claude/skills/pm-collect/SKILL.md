# pm-collect · 需求挖掘与收集

## 设计哲学

这一步只做**忠实记录**,不做价值判断。用户说"我需要一匹快的马",这一步只记录"用户说要一匹快的马"(原始诉求/Request),不替用户猜"他其实需要的是更快的交通方式"(真实需求/Need)——那个判断留给 `/pm-clarify`。提前下结论的记录,会把后续澄清步骤的起点污染成"确认我的猜测"而不是"挖掘真相"。

## 触发

**触发词**:记录需求、新增需求、需求池、有人要加个功能、用户反馈说、客户投诉、这个需求记一下
**不触发**:已经讨论清楚要不要做、只是想查已有需求状态(→ `/pm`)、要澄清一个已记录需求的细节(→ `/pm-clarify`)

## 输入要求

### 必须有(缺失则问,一次只问一个问题,不猜不假设)

- **提出人**:谁提的?如果是转述("运营同事说"),要追问转述人和原始提出人分别是谁,原始提出人才是记录对象
- **提出时间**:今天还是之前?
- **来源渠道**:枚举之一 —— 用户反馈 / 客户投诉 / 市场调研 / 竞品动态 / 业务运营需求 / 老板战略方向 / 技术重构性能优化
- **场景描述**:什么情况下产生这个需求(不是"要什么功能",是"什么场景逼出了这个诉求")
- **预期结果**:用户/提出人期望看到什么结果
- **原始诉求**:用户的原话或贴近原话的转述。这是本 skill 要记录的核心内容之一,必须单独确认并原文留存,不要等到写入步骤才补

### 可以推断(标注 `⚠️ 推断:[依据]`)

- **紧急程度**:取值为"高 / 中 / 低"三档(不用 P0-P3 —— 那是 `/pm-value` 阶段的产出,不是这一步的字段)。根据措辞语气、是否提及截止时间或已发生的负面后果推断对应档位。例如提到"上周被老板问了"这种已发生的具体后果,比单纯"挺麻烦的"语气更接近"高"档,但仍需在记录里写明推断依据,不能直接定成"高"

### 不允许猜测

- **原始诉求之外的任何"真实需求"判断**。即使你从场景描述里已经能看出表面诉求和真实需求可能不一致(比如"要导出 Excel"背后可能是"要看趋势图"),这一步也只记录表面诉求,把你的直觉写进本地 `01-collect.md` 文件末尾的一个"⚠️ 待澄清线索"小节里(不写入飞书,只是给 `/pm-clarify` 读取用的提示),不要替用户下结论

## 输出

- 飞书需求池新记录(字段见下方"写入飞书"小节)
- 本地 `pm-workspace/requirements/<REQ-ID>/01-collect.md`

## 执行流程

### Step 0 — 输入面板(开始前必须完成)

```
✅ 已确认:[字段] = [值]
❌ 必须明确:[字段] → 影响:[不明确会导致下游什么问题]
⚠️ 已推断:[字段] = [推断值](依据:[原因])
```

❌ 项一次只问一个,不批量甩问题给用户。全部 ❌ 清空后才能进入正式流程。

### Step 1 — 检查需求池是否已配置

读取 `pm-workspace/config.json`。如果文件不存在或 `feishu.bitable_app_token` 为空:

1. 问用户:"需求池还没建,你想建在哪个飞书文件夹里?"
2. 用 `lark-base` skill 的建表能力,创建一张多维表格,建表时建全部 26 个字段(采集组 8 个 + 澄清组 4 个 + 价值组 10 个 + 交付组 2 个 + 流程组 2 个,字段清单见 `pm-workspace/config.json.example` 的 `field_map`),参考 `lark-base` 的 `references/lark-base-field-schema.md` 确定每个字段的类型。本步骤(collect)只写入下方"写入飞书"小节列出的采集组 + 流程组字段,其余字段先建好留空,留给后续阶段(`/pm-clarify` 等)写入
3. 建 3 个视图:按优先级看板(分组字段=优先级)、待澄清(筛选=当前阶段=collect)、待评估(筛选=当前阶段=clarify)
4. 把生成的 `app_token` 和 `table_id` 写回 `pm-workspace/config.json`

如果已配置,跳到 Step 2。

### Step 2 — 生成需求 ID

格式:`REQ-YYYYMMDD-NNN-简短标题`。`YYYYMMDD` 用今天日期,`NNN` 是当天序号(查本地 `pm-workspace/requirements/` 目录下已有多少个同日期前缀的文件夹,取 +1,补零到 3 位),简短标题是场景的 4-8 字概括(如"订单导出")。

### Step 3 — 走输入面板,收集六个必填字段 + 一个推断字段

按"输入要求"小节的顺序逐一确认(提出人、提出时间、来源渠道、场景描述、预期结果、原始诉求,共六个必填字段;紧急程度为推断字段)。❌ 项一次问一个。

### Step 4 — 质量门检查(先检查,PASS 才写入)

**BLOCKER 判据**(命中任一,列出缺项,不放行,不执行任何写入 —— 不写飞书、不写本地文件,也不询问是否继续):
- 场景描述为空
- 紧急程度与场景描述矛盾(例如标"高"但场景描述里没有任何截止时间或负面后果线索,或反过来场景描述提到强烈负面后果却标"低")

**PASS 时**,继续执行 Step 5、Step 6。

### Step 5 — 写入飞书

创建一条新记录,字段:

| 字段 | 来源 |
|---|---|
| 需求ID | Step 2 生成 |
| 提出人 | Step 3 收集 |
| 提出时间 | Step 3 收集 |
| 来源渠道 | Step 3 收集(枚举值之一) |
| 场景描述 | Step 3 收集 |
| 预期结果 | Step 3 收集 |
| 紧急程度 | Step 3 推断,写入时带 "⚠️ 推断" 前缀 + 依据 |
| 原始诉求 | Step 3 收集(用户原话或贴近原话的转述,不要改写成功能描述) |
| 当前阶段 | 固定写 `collect` |
| 更新时间 | 当前时间 |

其余字段(澄清组/价值组/交付组)留空,后续阶段补。

### Step 6 — 写本地文件

Create `pm-workspace/requirements/<REQ-ID>/01-collect.md`,内容是 Step 0-5 的完整记录(输入面板 + 六个必填字段 + 推断字段及依据 + 原始诉求原文)。如果 Step 3 收集过程中产生了关于真实需求的直觉,追加一个"⚠️ 待澄清线索"小节记录,供 `/pm-clarify` 参考。

写完后,问用户:"`/pm-collect` 已完成,需求 ID 是 `<REQ-ID>`。是否现在进入 `/pm-clarify` 做需求澄清?"

## 常见设计错误

> 把"场景描述"写成"功能描述"。例如把"运营每周要手动复制订单数据做周报"写成"需要一个导出按钮"——这就是提前下结论,后续 `/pm-clarify` 会失去挖掘空间。

> 跳过"转述人 vs 原始提出人"的区分。二级转述的需求,提出人应该是原始说话的人,不是转达消息的同事。

## 参考:自检清单

执行 Step 4 质量门检查时参考(不是额外的步骤,BLOCKER 判据以 Step 4 为准):

- [ ] 场景描述是情境,不是解决方案
- [ ] 原始诉求是原话或贴近原话,没有被改写成功能点
- [ ] 紧急程度如果是推断的,依据写清楚了
- [ ] 需求 ID 格式正确且在本地目录里不重复
